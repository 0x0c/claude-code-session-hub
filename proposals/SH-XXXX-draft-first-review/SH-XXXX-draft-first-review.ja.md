## はじめに

Claude Codeは、プルリクエスト（PR）のドラフトが解除されたときにレビューします。すべてのセッションは、PRをドラフトとして作り、作業を終えてからドラフトを解除します。

## 動機

`main`のルールセットは、`claude review`チェックを必須とします。レビューはPRを開いたときだけ動いたので、チェックは最初のコミットに残り、その後のプッシュでPRはマージできなくなりました。`@claude review`で依頼したレビューも解決になりません。GitHubは、`issue_comment`による実行をデフォルトブランチに記録するからです。PR #45は、レビューが成功した後も、この理由で止まりました。

この変更が入ると、ドラフトの手順を終えたPRの先頭コミットに`claude review`チェックが付き、レビューは完成した作業を対象とします。

## 詳細設計

- **トリガー。** ワークフローは、`opened`と`reopened`に`ready_for_review`を加えます。プッシュでは、これまでどおりレビューを始めません。
- **ドラフト。** ジョブの条件により、ドラフトに対する`pull_request`イベントをスキップします。早めのレビューがほしいときは、ドラフトに`@claude review`とコメントできます。
- **セッション。** `AGENTS.md`のGitの節で、すべてのセッションに同じ手順を示します。
  1. 利用者にPRを頼まれたら、`gh pr create --draft`で作る。
  2. コミットはすべてドラフトにプッシュし、`scripts/check.sh`を通す。
  3. `gh pr ready`を実行する。
- **後からの変更。** ドラフトを解除したPRを変更するセッションは、`gh pr ready --undo`を実行し、修正をすべてプッシュしてから、もう一度`gh pr ready`を実行します。この手順により、新しい先頭コミットのレビューが1回始まります。
- **提案用のスキル。** `ideation`、`implement-proposal`、`propose-and-build`は、ドラフトの手順を参照します。ドラフトを作ると、レビューの開始前に提案へPR番号を書き込めます。
- **制限。** GitHubは、スキップされたジョブを合格として扱います。そのため、`gh pr ready`の後も、新しいレビューのチェックが登録されるまで、ドラフトでスキップされたチェックが先頭コミットに合格として残ります。この間に自動マージなどでマージすると、レビューを経ません。この隙間は許容し、レビューの後に手動でマージします。ボットのPRや通常のレビューコメントによるスキップは、変更前と同じく、必須チェックを満たす可能性が残ります。

## 検討した代替案

- **プッシュのたびにレビューする。** `synchronize`トリガーを使えば、チェックは先頭コミットに付きます。しかし、途中のプッシュのたびにトークンを使い、レビューが自分の指摘への修正に再び指摘することもあります。
- **必須チェックから外す。** レビューが動く前にPRをマージできてしまいます。
- **フックで`--draft`を強制する。** フックは、`gh`コマンド以外で作ったPRを見逃します。まずは、すべての経路に及ぶ共通の指示から始めます。
