## はじめに

トークンのないハブは、`Host`ヘッダーがループバックインターフェースを指さないリクエストをすべて拒否します。この検査で、WebページがDomain Name System（DNS）リバインディングを使ってハブを読んだり変更したりすることを防ぎます。

## 動機

DNSリバインディングでは、まず`http://evil.example:8765`のページを読み込ませ、その後で所有者が`evil.example`を`127.0.0.1`に向けます。ブラウザーは、ハブをそのページと同一オリジンとみなします。ハブはループバックインターフェースで待ち受け、初期設定ではトークンを必要としません。そのため、このページは全メッセージを読み、偽のメッセージを送り、セッションを削除できます。

この変更が入ると、`Host: evil.example:8765`のリクエストには`403`を返します。ダッシュボードとコマンドは今までどおり動きます。

## 詳細設計

- **条件：** ハブにトークンがないときです。トークンのあるハブは任意の名前で公開でき、リバインディングしたページはそのトークンのクッキーを持ちません。
- **場所：** リクエストヘッダーを読んだ直後、メソッドやパスを見る前です。`/healthz`や今後追加するものも含め、すべてのエンドポイントに効きます。
- **受け付ける名前：** `127.0.0.1`・`localhost`・`::1`です。大文字と小文字は区別しません。ポートは比べないため、ポート転送も使えます。
- **拒否：** それ以外の名前と、ヘッダーがない場合や不正な場合に`403`を返します。本文のJavaScript Object Notation（JSON）のエラーで、2つの対処を示します。その後、ハブは接続を閉じます。読み残した本文をリクエストとして解釈しないためです。

トークンのないハブの前にリバースプロキシーや独自のホスト名を置く構成は動かなくなります。その場合は`HUB_TOKEN`を設定します。設定するまでの間、クライアントはpushへの`403`を、ハブに届かない場合と同じに扱います。メッセージは共有ストアかoutboxに入り、失われません。`session-hub doctor`は、このハブを応答なしと表示します。

別オリジンのページが`http://127.0.0.1:8765/api/events`へ直接POSTする場合、`Host`はループバックです。このリクエストはDNSリバインディングではないため、この提案の対象外です。

## 検討した代替案

- **外部の`Origin`を拒否する。** ブラウザーは同一オリジンの`GET`に`Origin`を付けません。リバインディングしたページは、引き続き全メッセージを読めます。
- **トークンを必須にする。** 既存のすべての構成に新しい設定が必要になります。
- **エンドポイントごとに検査する。** 新しいエンドポイントで検査が漏れるおそれがあります。
