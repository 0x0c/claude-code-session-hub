# Session Hubの設計

親セッション（オーケストレーター）は、複数の子セッションを同時に走らせることがよくあります。本書は、親と人間がすべての子の状態を**一目で**、しかも**できるだけ少ないトークンで**把握する仕組みを設計します。子は自分の状態をローカルのハブサーバーへ報告します。ハブサーバーは報告を保存してリアルタイムのダッシュボードへ送り、親は子が必要としたときだけ数行の要約を読みます。

> 実装状況: §8のフェーズ0、1、3、4の大部分を実装済みです。push型のハブサーバー、タイムラインビュー付きのダッシュボード、報告用のスキルとhookがそろっています。
> 使い方は[README](../README.ja.md)を、用語は[付録A](#付録a-用語集)を参照してください。

## 0. 目的と設計原則

| 目的 | 知りたいこと |
|---|---|
| トークンの節約 | 親が子のトランスクリプトを読まず、必要もなく起こされないこと |
| 人間の介入が必要か | 子が人間を待って止まっていないか。判断、認証情報、権限、仕様の確認など |
| プルリクエスト（PR）をレビューに出せるか | 継続的インテグレーション（CI）、自己レビュー、未解決事項がすべて片づき、PRをレビューに出せるか |
| 稼働状況 | 各子が今何をしているか、止まっていないか（ハートビート） |
| 残作業 | 残りのタスク数と規模、次の一手 |

次の6つの原則に従います。

1. **pullを基本とし、親へのpushは例外に限ります。** 子は共有ストアに状態を書くだけです。子がトークンを使って親を起こすのは、人間待ち、レビュー可、失敗、完了の4つの遷移のときだけです。
2. **集計と描画は大規模言語モデル（LLM）ではなくスクリプトが担います。** ダッシュボードの生成は決定的な処理なので、トークンを消費しません。
3. **意味はLLMが書き、事実はスクリプトが集めます。** フェーズと質問文は子エージェントが書きます。トークン数、コミット、PRとCIの状態、最終更新時刻は、hookとスクリプトが自動で集めます。
4. **固定スキーマ、列挙値、短いテキスト。** 自由記述は1行の要約と質問文に限り、それぞれに文字数の上限を設けます。
5. **段階的開示。** 読み手は一覧（1セッション1行）から詳細（JavaScript Object Notation（JSON）レコード1件）、トランスクリプト（リンク）へと進みます。親は通常、一覧の「要対応」の行だけを読みます。
6. **自己申告だけを信用しません。** 「レビュー可」と判定するには、子自身の申告と、CIの成功のような機械的なゲートの両方が必要です。

## 1. 子が記録する情報（ステータスレコード）

各セッションはステータスレコードを1つ持ちます。ステータスレコードはJSONオブジェクトで、フィールド`v`がスキーマのバージョンを表します。

### 1.1 フィールド

| グループ | フィールド | 書き手 | 説明 |
|---|---|---|---|
| 識別 | `v`, `session_id`, `parent_id`, `title`, `task_ref` | 起動時（親） | `task_ref`はIssue番号かタスク識別子（ID） |
| 場所 | `repo`, `branch`, `base` | 起動時 / hook | |
| 状態 | `state` | 子（CLI） | §1.2に挙げる値のいずれか |
| | `phase` | 子 | `plan` / `implement` / `test` / `fix` / `docs` / `self_review`のような、選択肢の少ない列挙 |
| | `summary` | 子 | 子が今何をしているか。**80文字以内** |
| | `next` | 子 | 次の一手。80文字以内 |
| 進捗 | `tasks.done`, `tasks.total`, `tasks.items[]` | 子またはhook | 各項目は`{t: "short name", s: "todo|doing|done|skip", size: "S|M|L"}` |
| | `remaining` | スクリプト | 未完了の項目の規模の合計（たとえばS=1、M=3、L=8） |
| 人間待ち | `attention.kind` | 子 | `decision` / `clarification` / `credential` / `permission` / `review` / `external`（たとえば他チーム待ち） |
| | `attention.question`, `attention.options[]`, `attention.default`, `attention.since` | 子 | 選択肢の提示を推奨します。回答が1語で済み、往復ごとのトークンが減ります |
| | `attention.blocking` | 子 | `true`: 子は完全に止まっています。`false`: 子は既定値で作業を続けながら確認を待っています |
| 阻害要因 | `blocked_on` | 子 | 別のセッションIDか外部要因（`session:xxx`, `ci`, `upstream`） |
| PR | `pr.number`, `pr.url` | hook | |
| | `pr.ci` | スクリプト | `pending` / `pass` / `fail` / `none` |
| | `pr.mergeable`, `pr.unresolved_threads`, `pr.review` | スクリプト | GitHubから取得 |
| | `ready.self_review`, `ready.tests_added`, `ready.description` | 子 | 子が自己申告するチェックリスト |
| | `ready.gate` | スクリプト | §4のゲートの結果（`ready` / `not_ready:<reason>`） |
| コスト | `usage.input`, `usage.output`, `usage.cache_read`, `usage.cache_write`, `usage.cost_usd` | hook | トランスクリプト（`transcript_path`）にあるusageの合計 |
| | `usage.context_pct` | hook | コンテキストウィンドウの使用率。圧縮が近いセッションを検知します |
| 健全性 | `heartbeat` | hook | 最後のターンが終わった時刻 |
| | `last_error` | 子 / hook | 直近の失敗（120文字以内） |
| | `confidence` | 子 | `high` / `med` / `low`。確信度の低いセッションを人間が先に見ます |
| 管理 | `seq`, `updated_at` | CLI | 単調増加します。順序の逆転した書き込みと重複した書き込みを拒否します |
| | `links.session`, `links.artifacts[]` | hook | トランスクリプトと成果物へのリンク |

### 1.2 `state`の値と遷移

```
queued → planning → working ⇄ waiting_ci
                      │  ↑         │
                      ▼  │         ▼
              needs_human ─┘   review_ready → in_review → changes_requested ─┐
                      │                          │                       │
                      ▼                          ▼                       │
                   blocked                     done (merged)   ←── working ┘
任意の状態 → failed / abandoned
```

| state | 意味 | 親を起こすか |
|---|---|---|
| `queued` | 開始待ち | いいえ |
| `planning` / `working` | 作業中 | いいえ |
| `waiting_ci` | CI待ち（子の手は空いています） | いいえ |
| `needs_human` | 人間の判断が必要 | **はい** |
| `blocked` | 別のセッションか外部要因を待っています | 長く続いた場合のみ（スクリプトが判断） |
| `review_ready` | レビューに出してよい（ゲートを通ったときだけ確定） | **はい** |
| `in_review` / `changes_requested` | レビュー中 / レビューコメントへの対応中 | コメントが届いたときのみ |
| `done` | 完了 | **はい**（複数をまとめて1通にします） |
| `failed` / `abandoned` | 失敗 / 放棄 | **はい** |

## 2. トランスポートの比較

トランスポートとは、状態の更新が通る経路です。9つの候補を比較しました。

| トランスポート | 方向 | 親のトークン | 即時性 | 耐久性 | 人間にとっての読みやすさ | 備考 |
|---|---|---|---|---|---|---|
| **A. Gitの専用ブランチ**（orphanの`hub/status`、1セッション1ファイル） | 子→ストア | 0 | 低（push間隔） | 高（履歴=イベントログ） | 中 | どの環境でも動きます。1セッション1ファイルなので衝突はほぼ起きません。pushに失敗したらrebaseして再試行します |
| B. 作業ブランチ内のステータスファイル | 子→ストア | 0 | 低 | 高 | 低 | 非推奨です。PRの差分を汚します |
| **C. Artifactの共有データベース**（ArtifactData） | 子→ダッシュボード | 0 | 高 | 中 | **高**（そのままWebページになる） | ダッシュボード自体をArtifactにすれば描画も即時です。子セッションが同じアカウントで書き込めることが前提です |
| D. `send_message`（子→親） | 子→親 | **毎回**（親のターンが走る） | 最高 | 低（会話内のみ） | 低 | エスカレーション専用にします |
| E. `send_message`（親→子） | 親→子 | 子の側のみ | 最高 | 低 | — | 回答と指示（コマンド）に使います |
| F. GitHubのラベル / PR本文 / Issueコメント | 子→GitHub | 0 | 中 | 高 | 高（GitHub上） | `hub:needs-human`のようなラベルはGitHubの通知と連携できます。PRができる前は使えません |
| G. クラウドセッションアプリケーションプログラミングインターフェース（API）のポーリング（`get_session`の`status_bucket`、`kinds`で絞り込んだ`list_events`） | 親が取得 | 小〜大 | 中 | — | — | 子の協力なしに得られる真値です。ただしModel Context Protocol（MCP）のツールなのでLLMが呼ぶ必要があり、`list_events`は重いです。`get_session`に限れば、ポーリングは安く済みます |
| H. ローカルのトランスクリプト（`~/.claude/projects/**/*.jsonl`） | スクリプトが直接読む | 0 | 高 | 高 | — | ローカルの並列実行のみです。usageや最後のツール呼び出しのような事実が得られます |
| **I. ハブサーバーへのHypertext Transfer Protocol（HTTP） push**（`POST /api/events`） | 子→サーバー→ブラウザー | 0 | **最高**（受信と同時に配信） | 高（サーバーがストアに追記） | **高** | 子からサーバーへ到達できる必要があります（§9） |

### 採用: push（I）を主なトランスポートにする

当初はGitのストアをポーリングする案（A）を推奨していました。**ダッシュボードを即時に更新する**ため、pushに切り替えました。

- **子 → ハブ**: 子は状態が変わるたびに、`session-hub`コマンドでハブサーバーへイベントをPOSTします（I）。ハブサーバーはイベントを検証してストアに追記し、接続中のすべてのブラウザーへServer-Sent Events（SSE）でただちに配信します。**ハブサーバーもブラウザーもポーリングしません。**
- **配信に失敗したとき**: 子は送れなかったイベントをoutbox（ローカルのJSON Lines（JSONL）ファイル）に残し、次の送信時に先に再送します。
- **耐久性**: ストアは追記のみのJSONLです。必要なら、Aと同じようにGitでストアを共有、保管することもできます（補助機能の`--pull-every`オプション）。
- **エスカレーション**: 親を起こすべき遷移のときだけDを使います（§3.3）。
- **回答と指示**: Eを使います。
- **死活の真値**: 親は必要なときだけ`get_session`（G）を呼び、その`status_bucket`を報告された状態と突き合わせます。
- **人間への通知**: ダッシュボードのブラウザー通知を使い、Fのラベルで補います。

## 3. プロトコル

### 3.1 構成要素

```
┌──────────── 子セッション ──────────────┐
│ エージェント ── session-hub report ... ─┐   意味: state / phase / summary / 質問
│ Stop hook ───── session-hub hook stop ─┤   事実: heartbeat / トークン使用量（0トークン）
│ PostToolUse ─── session-hub hook todo ─┤   TodoWriteなど → 進捗（0トークン）
│                                        ▼
│                    POST /api/events ─────────────┐   失敗時はoutboxに保存し、次回に再送
│ 重要な遷移のみ ── send_message ───► 親（1行）
└────────────────────────────────────────┘          │
                                                     ▼
┌──────────── ハブサーバー（session-hub serve）──────────────┐
│ 検証 → seqと時刻を採番 → ストアへ追記（events/*.jsonl）     │
│ → 状態に畳み込み、差分をSSEでブラウザーへただちにpush       │
└───────────────┬─────────────────────────────────────┘
                ▼ GET /api/stream（SSE）          ▲ GET /api/snapshot
         ブラウザーのダッシュボード          親: session-hub attention
```

- **イベントソーシング**: ハブは状態を保存しません。読み出すたびに、追記のみのイベント列を畳み込んで状態を求めます。イベント列はタイムラインビューの元データにもなるので、読み手は何がいつ変わったかを正確にたどれます。
- **書き手ごとのファイル**: `events/<session_id>.jsonl`には子のイベントが、`events/<session_id>@parent.jsonl`には親の回答と指示が入ります。各ファイルの書き手は常に1人なので、Gitでストアを共有しても衝突しません。
- **時刻の採番**: ハブサーバーは、ストア全体で単調増加するミリ秒単位の時刻を付けます。そのため、到着順と表示順は常に一致します。

### 3.2 子 → ハブ（`session-hub report`ほか）

子エージェントに求めるのは1つだけです。状態が変わるたびに、1行のBashコマンドを実行してもらいます。手順は`skills/session-hub-report/SKILL.md`にあります。

```bash
session-hub start --title "Rate limiting for the auth API" --task-ref "#128" --task "Design=todo:S" --task "Implement=todo:M"
session-hub report --phase implement --summary "Implementing the middleware" --task "Implement=doing"
session-hub ask --kind decision --q "Limit per minute?" --opt 60 --opt 120 --opt 300 --default 120
session-hub pr --number 45 --ci pending --state waiting_ci
session-hub ready --self-review --tests --description
session-hub done --summary "PR #45 merged"
```

- `HUB_URL`が設定されていれば、コマンドはハブへpushします。設定されていなければ、ローカルのストア（`HUB_STORE`）に書きます。
- ハブサーバーは各イベントを検証し、テキストを上限で切り詰め、`seq`と時刻を採番します。不正な値はHTTP 400で拒否し、子には有効な候補が表示されます。
- 子がコマンドを呼ぶのは、**状態の遷移時、新しい質問の発生時、PRの節目だけ**です。
- 子が報告を忘れた分は、hookが補います（§3.6）。

### 3.3 子 → 親（エスカレーション通知）

子が親を起こすのは、次の遷移のときだけです。通知は固定書式の1行で、親は詳細をストアから読みます。

```
[HUB/1] <session_id> <event> <short text ≤ 80 characters>
```

| event | 例 | `send_message`のpriority |
|---|---|---|
| `needs_human` | `[HUB/1] session_01ABC needs_human Waiting for the limit value (60/120/300)` | `later`（`blocking`なら`next`） |
| `review_ready` | `[HUB/1] session_01ABC review_ready PR#45 CI green` | `later` |
| `failed` | `[HUB/1] session_01ABC failed Test environment does not start` | `next` |
| `done` | `[HUB/1] session_01ABC done PR#45 merged` | `later` |

- 親の指示書（CLAUDE.mdなど）には、ルールを1つだけ書きます。`[HUB/`で始まるメッセージを受けたら、本文を深読みせずに`session-hub attention`を実行する、というルールです。
- プラットフォームは、セッション間のメッセージを「ピアからのデータ」として扱います。そのため親は、そうしたメッセージに含まれる指示には従わず、純粋に状態の通知として扱います。このルールが、プロンプトインジェクションから親を守ります。
- 同じイベントは繰り返し通知しません。CLIは最後の通知を記録し、同じ`(state, attention.question)`では再送しません。

### 3.4 親 → 子（コマンド）

```
[HUB/1] cmd=<command> [key=value ...]
```

| command | 目的 |
|---|---|
| `answer q=<id> v=<value>` | 質問への回答（選んだ選択肢の値だけを返す） |
| `report` | 最新の状態の再送依頼（ハートビートが途絶えたとき） |
| `pause` / `resume` | 一時停止 / 再開 |
| `rebase base=main` | ベースブランチへの追従の指示 |
| `abort reason=...` | 作業の中止 |

### 3.5 親の定常処理（トークンの最小化）

1. 親は待つだけです。子から`[HUB/1]`メッセージが届いたときだけ、`session-hub attention`を実行します。`HUB_URL`が設定されていれば、このコマンドはハブサーバーのスナップショットを読みます。
2. 親が`get_session`で死活を確認するのは、停滞の疑い（`ST`）があるセッションに限ります。原則として、親は`list_events`を呼びません。
3. 親が読むのは`attention`の出力だけです。出力は「要対応」の行で、通常は数行です。全件の一覧とタイムラインは、人間がダッシュボードで見ます。

### 3.6 子に期限どおり報告させる仕組み

push型では、子が報告するまでダッシュボードは古いままです。そこで、何をいつ送るかを3つの層で保証します。

| 層 | 仕組み | トークン | 保証する内容 |
|---|---|---|---|
| 1. 自動送信（hook） | `Stop` hookがハートビートとトークン使用量を送ります。`PostToolUse(TodoWrite, TaskCreate, TaskUpdate)`が進捗と作業中のタスク名を送り、作業が始まるとplanning→workingへ移します | 0 | 子が生きているか、どこまで進んだか |
| 2. 指示（スキル + 起動プロンプト） | `skills/session-hub-report/SKILL.md`（いつ何を送るかの表）と`prompts/child-append-system-prompt.md`（5つの常駐ルール）。セッションが未登録なら、`SessionStart` hookが`start`の実行を促す2行を注入します | 少量 | 意味（フェーズ、質問、PR、完了） |
| 3. ターン終了時のガード | 最後に報告した状態がplanningかworkingのまま、または未登録のまま子がターンを終えようとすると、`Stop` hookが**1回だけ**ブロックして報告を求めます。`stop_hook_active`が無限ループを防ぎ、`HUB_STOP_GUARD=0`でガードを無効にできます | 1ターン分（必要なときのみ） | 作業中のまま放置されるセッションがなくなり、スピナーの表示が正しく保たれます |

- `HUB_URL`と`HUB_STORE`のどちらも未設定なら、hookは何もしません。そのため、プラグインを常に有効にしておいても、ほかの作業には影響しません。
- hookは、ネットワークの失敗や例外でセッションを止めません。イベントをoutboxに積むか、終了コード0で黙って終了します。
- ガードは「子が最後に報告した内容」を子のローカル状態（`~/.cache/session-hub/state-<id>.json`）から読み、ネットワークを使いません。

### 3.7 コレクション: 更新をためる場所と見せ方

セッションごとの状態とは別に、**セッションをまたいで1か所に集めたい情報**があります。作業で判明した知見、注意点、決定事項です。この情報のために専用の機能は作りません。代わりに「受け取った更新をためる場所」を一般化し、**コレクション**（collection）として扱います。

```
             ┌─ match ──┐   ┌── reduce ───┐   ┌── view ──┐
イベント列 ──┤ どれを   ├──►│ どう        ├──►│ どう     ├──► ダッシュボードのタブ
（唯一の正） │ 集めるか │   │ まとめるか: │   │ 見せるか:│
             └──────────┘   │ log/latest/ │   │ cards/   │
                            │ aggregate   │   │ table    │──► sinks（Markdown / JSONLへ書き出し）
                            └─────────────┘   └──────────┘
```

- **唯一の正はイベントストアです。** コレクションはストアの上に重ねる投影です。コレクションの定義を変えると、過去のイベントからコレクションを作り直します。書き出し先を増やしても、子の送り方（プロトコル）は変わりません。
- **定義は宣言的なJSONです**（ストア直下の`collections.json`）。ユーザーはコードを書かずに、コレクションを追加、上書き、無効化できます。

| 要素 | 内容 | 例 |
|---|---|---|
| `match` | 集めるイベントの条件。`type`、`kind`、`tags_any`、`session`、`status` | `{"type": ["finding"], "kind": ["decision"]}` |
| `reduce` | まとめ方。`log`（時系列のまま残す）、`latest`（キーごとに最新の1件）、`aggregate`（キーごとに1件へ統合） | ナレッジは`aggregate`を使い、キーは`key\|title`（明示的なキーがなければタイトル） |
| `view` | 表示形式。`cards`（`group_by`でグループ分け）、`table`（指定した`columns`で表示） | ナレッジは種類別にグループ分けしたカードで表示します |
| `sinks` | 追加の書き出し先。`markdown` / `jsonl`（ストア内のパス）。シンクのファイルは内容が変わったときだけ書き換えます | `KNOWLEDGE.md`を最新に保ち、リポジトリやWikiで公開します |

**`aggregate`の統合規則**: 本文などのフィールドは最新の報告で上書きしますが、空の値では上書きしません。`tags`と`scope`はすべての報告の和集合になり、報告元はすべて残ります。複数のセッションが同じ注意点に気づくと、報告は1件にまとまり、たとえば「2 セッション / 2 回報告」と表示されます。この件数が重要度の自然な指標になります。同じタイトルで`status: obsolete`を送ると、その項目は廃止になります。廃止した項目は既定の表示と`knowledge`の出力から外れますが、履歴は残ります。

**組み込みコレクション「ナレッジ」**: 子が`session-hub learn`で送る`finding`イベントを集約します。

| `kind` | 表示名（画面のラベル） | 記録するもの |
|---|---|---|
| `caveat` | 「注意点」 | 知らないと誰でもはまる罠 |
| `issue` | 「未解決の問題」 | 子が自分のタスクの外で見つけ、そのまま残した問題 |
| `decision` | 「決定事項」 | 決めたことや回答をもらったこと（理由つき） |
| `howto` | 「手順・ノウハウ」 | 再現、セットアップ、調査の手順 |
| `insight` | 「知見」 | 設計、性能、仕様について分かった事実 |

`finding`は`{kind, title(≤80), body(≤600, newlines allowed), tags[], scope, key, status}`のフィールドを持ちます。

**ナレッジの読み方（トークンの節約）**: 子は作業を始める前に`session-hub knowledge --scope <the area it will touch>`を実行し、関係する項目だけを数行で読みます。親は新しい子を起動するとき、関係する項目だけを`prompt`に添えます。親も子も、全項目をコンテキストに読み込むことはしません。

**定義例**（`collections.json`）:

```json
[
  {"name": "knowledge", "sinks": [{"type": "markdown", "path": "KNOWLEDGE.md"}]},
  {"name": "decisions", "label": "Decision log",
   "match": {"type": ["finding"], "kind": ["decision"]},
   "reduce": {"type": "log", "payload": "finding"},
   "view": {"type": "table", "columns": ["title", "body", "reporters", "last_ts"]}},
  {"name": "prs", "label": "PR status", "match": {"type": ["pr"]},
   "reduce": {"type": "latest", "key": ["session_id"]},
   "view": {"type": "table", "columns": ["session_id", "pr", "last_ts"]}}
]
```

### 3.8 ローカル運用（現在の構成）

| 項目 | 内容 |
|---|---|
| 子の実行場所 | ユーザー自身のコンピューター。人間が並べて起動する`claude`セッションか、親が`claude -p --append-system-prompt ...`でバックグラウンド起動するセッションです |
| 共有設定 | `~/.claude/settings.json`の`env`に`HUB_URL=http://127.0.0.1:8765`、`HUB_STORE=~/.session-hub`、`HUB_AUTOSTART=1` |
| ハブサーバー | 127.0.0.1でのみ待ち受けます（トークン不要）。`HUB_AUTOSTART=1`なら、最初に始まったセッションのSessionStart hookがバックグラウンドでハブサーバーを起動します。ポートの取り合いにより、2つ目のインスタンスは起動しません |
| メッセージの配送 | 1. ハブサーバーへpushします（即時に表示）。2. pushに失敗したら、共有ストアへ直接書きます。3. ストアも未設定なら、outboxに積みます |
| ハブサーバー停止中に送ったメッセージ | ストアに残るので失われません。ハブサーバーの起動時、次のpush、または30秒ごとの再確認で画面に表示されます |
| 親への通知 | 使える場合は、ローカルのセッション間メッセージで`[HUB/1]`行を送ります。使えない場合は、ダッシュボードのブラウザー通知とタブのタイトル（要対応のセッション数）で人間が気づきます |
| 導入 | Agent Package Manager（APM）で`apm install 0x0c/claude-code-session-hub --target claude`を実行します（プロジェクト単位。スキルは`.claude/skills/`へ、hookは`.claude/settings.json`へ、パッケージ本体は`apm_modules/`へ入ります）。またはClaude Codeのプラグインとして導入します |
| 確認 | `session-hub doctor` |
| 注意 | Agentツールのサブエージェントは親とセッションIDを共有するため、ダッシュボードには別セッションとして表示されません。必要なら`--session`で固有のIDを渡します |

## 4. スクリプトが機械的に判定する項目

### 4.1 レビューゲート（`ready.gate`）

ゲートは、次の条件をすべて満たしたときだけ`review_ready`を確定します。満たさない場合は、最初に満たさなかった条件を記録します。

1. PRが存在し、ドラフトではありません（またはドラフトを解除する直前です）。
2. CIが`pass`です。
3. `mergeable`がtrueです。コンフリクトがなく、ブランチがベースから大きく遅れていません。
4. 未解決のレビュースレッドがありません。
5. `attention`が空です。
6. 子の自己申告`ready.self_review`、`ready.tests_added`、`ready.description`がすべてtrueです。
7. `tasks`に`todo`や`doing`の項目が残っていません（`skip`は許容します）。

### 4.2 停滞と異常の検知

| 条件 | 判定 |
|---|---|
| `state=working`かつ`heartbeat`がN分以上前 | `stale?`。親が`get_session`で確認します |
| `get_session.status_bucket=failed`なのに`state≠failed` | 子が報告する前にクラッシュしています |
| `needs_human`がM時間以上続く | 優先度を上げて表示します |
| `usage.context_pct` > 80 | 圧縮か作業の分割を検討します |
| `usage.cost_usd`が予算を超えた、または進捗に比べて高すぎる | 効率を`cost_usd / tasks.done`として表示します |
| 残りの`tasks`が長い間減らない | ループや迷走の疑い |

### 4.3 優先順位（ダッシュボードの並び順）

`needs_human(blocking)` > `failed` > `review_ready` > `stale?` > `needs_human(non-blocking)` > `changes_requested` > `blocked` > `working` > `waiting_ci` > `done`

## 5. ダッシュボード

ダッシュボードは英語と日本語に対応しています。ブラウザーの言語に合わせて表示し、ヘッダーのボタンか`?lang=en`/`?lang=ja`のパラメーターで切り替えられます。本節では、画面のラベルを「」で囲んで示します。

### 5.1 出力形式

| 形式 | 用途 |
|---|---|
| `session-hub serve`のダッシュボード | 人間向け。pushを受けるたびに反映します（SSE） |
| `session-hub export --out dashboard.html` | スナップショットを埋め込んだ単体のHyperText Markup Language（HTML）ファイル（共有と保管用。更新はしません） |
| `GET /api/snapshot` | 機械向けのJSON |
| `session-hub attention` | 親のLLM向け。要対応のセッションだけを1件1行で出します |
| `session-hub log [<session_id>]` | ターミナルでタイムラインを追います |

### 5.2 画面構成

- **ヘッダー**: 接続状態（リアルタイム / 再接続中 / ポーリング）、セッション数、要対応の数、作業中の数、トークンの合計、最終更新を表示します。
  - タブのタイトルにも、`(3) Session Hub`の形で要対応の数を表示します。
  - 任意のブラウザー通知で、人間待ち、レビュー可、失敗、完了、停滞への遷移を知らせます。
- **セッション一覧**（左）: 「要対応」「作業中・待機」「完了」に分け、それぞれを§4.3の優先順位で並べます。
  - 各カードには、状態バッジ、タスクの進捗バー、残作業、PRとCI、トークンと費用、最終更新、未回答の質問（選択肢、既定値、回答用のコマンドつき）を表示します。
  - **手を動かしている状態（planning / working / changes_requested）のセッションには、スピナーを表示します。** CI、阻害要因、人間を待っているだけのセッションには表示しません。停滞の疑いがあるセッションにも表示しません。
  - ゲート（§4.1）を通らず自己申告だけに基づく「レビュー可」は、「レビュー条件未達」と表示し、満たしていない理由を添えます。
- **タイムライン**（右）: 子から届いた報告を、2つの形式で時系列にたどります。
  - **フィード**: イベントを日付ごとにまとめて並べます。各行には時刻、セッション、種別、本文、そのイベントで変わったこと（状態A→B、フェーズ、タスク数、解決した質問）を表示します。「詳細」を押すと生のイベントJSONを開きます。新着のイベントはハイライトします。読み手が下にスクロールしている間は、画面を動かさずに「新着 N 件」バーで新着を知らせます。絞り込みには、セッション、イベント種別、全文検索、ハートビートの表示（連続するハートビートは1行にまとめる）、新しい順または古い順があります。
  - **スイムレーン**: セッションごとに1本の横帯を描き、状態の変化を色の区間で示します。点はイベントを表します（質問=橙、回答=青）。ホバーすると詳細を表示し、クリックするとフィードの該当行へ移動します。人間待ちの長さや停滞が一目で分かります。
- **コレクションのタブ**（右パネル）: 定義した各コレクションのタブが自動で加わります。たとえば「ナレッジ (6)」です。
  - `cards`ビューは項目ごとに1枚のカードを表示し、グループ分けします（ナレッジは種類別）。各カードには、本文、タグ（クリックで検索）、対象範囲、報告したセッションとその数、最終更新を表示します。
  - 報告したセッションの名前をクリックすると、タイムラインの該当イベントへ移動します。絞り込みにはセッション、全文検索、グループがあり、廃止した項目の表示を切り替えるトグルもあります。
  - pushで届いた項目は、その場でハイライトします。
- **メッセージ受信時のグロー**: サブセッションからメッセージが届くと、4つの要素が約6秒間、遷移後の状態の色で光ります（人間待ち=橙、失敗=赤、レビュー可=緑など）。
  - そのセッションのカード
  - タイムラインの該当行
  - スイムレーンの帯
  - メッセージが入ったコレクションの項目

  グローは再描画されても途切れず、続きから光り続けます。メッセージが続けて届くと、最新のメッセージでグローをやり直します。ハートビート（hookによる自動送信）は光りません。動きを減らす設定（prefers-reduced-motion）では脈動させず、枠線だけを表示します。
- ダッシュボードはスマートフォンの幅（390px）でも横スクロールなしで読めます。ライトとダークの両方のテーマに対応しています。

### 5.3 `session-hub attention`の出力（親が読むもの）

各行は2文字のコードで始まります。`NH`（人間待ち）、`FL`（失敗）、`RR`（レビュー可）、`ST`（停滞）のいずれかです。

```
NH session_01ABC #128 decision q=4 "Limit per minute?" [60|120*|300] 38m
FL session_04XYZ npm ci failed with ERESOLVE (peer dependency conflict)
RR session_01DEF #131 PR#45 ci=pass CI green, self-review done
ST session_01GHI 47m since heartbeat
```

## 6. トークンを節約するその他の策

| 策 | 効果 |
|---|---|
| 子はトランスクリプトを要約せず、状態をCLIの引数で渡します | 子の出力トークンが減ります |
| 質問に選択肢と既定値を添えます | 人間や親との往復が1語に縮みます |
| `attention.blocking=false`を使います（既定値で進め、後から見直せる判断の場合） | 待ち時間が減り、再開にかかる無駄なコストも減ります |
| 原則として親は`list_events`を呼びません（どうしても呼ぶなら`kinds`を`result`に絞ります） | 親の入力トークンが減ります |
| 通知をまとめます（複数の`done`通知を1通にまとめるなど） | 親が起こされる回数が減ります |
| 子のモデルとeffortをタスクの規模（`size`）で選びます | 単価が下がります |
| hookでusageを記録し、タスクあたりのコストを表示します | コストの高いパターンが見えます |
| 報告していない子に、Stop hookが1回だけ報告を求めます | 報告漏れを防ぎます。報告の要求には1ターン分のコストがかかるので、報告なしに状態が変わったときだけ発動します |

## 9. 未決事項

1. **ハブサーバーの置き場所**: **当面はローカル運用に決定しました。** サブセッションはユーザー自身のコンピューターで動き、すべてのセッションが1つの`HUB_STORE`を共有します。
   - ハブサーバーは`127.0.0.1`でのみ待ち受け、子は`HUB_URL=http://127.0.0.1:8765`へpushします。コンピューターを外部に公開することはありません。
   - ハブサーバーが止まっている間、子は共有ストアへ直接書きます。そのメッセージは、ハブサーバーの起動時か次のpushで画面に表示されます（§3.8）。
   - クラウドの子セッションについては、常設のサーバーとArtifactの共有データベースの2案を、将来の検討事項として残します。
   - どちらの案でも、子の環境のネットワーク許可リストにそのホストを加え、トークンは環境変数ではなくネットワークシークレットとして登録するのが望ましいです。
2. **実行環境**: 子は主にクラウドセッション（`create_session`）になるのか、ローカルの並列実行も対象にするのか。ローカルの実行だけなら、`HUB_STORE`を共有すれば十分です。
3. **GitHubの情報の自動取得**（フェーズ2）: ハブサーバーがGitHub APIを呼ぶべきか、親が情報を取得して`session-hub pr`で記録すべきか。
4. **自動化の範囲**: `review_ready`のとき、ハブがPRのドラフト解除やレビュアーの割り当てまで行うべきか。
5. **予算**: セッションごとと全体のコストの上限、および上限を超えたときの挙動（通知だけか、停止するか）。現在のhookはトークン数だけを記録し、金額は任意です（`--cost`）。
6. **ナレッジの整理**: 似た内容でも表現の違う知見は、別の項目になります。親（または人間）が定期的に`--key`で統合し、`--obsolete`で廃止する運用で十分か。それとも類似度で項目をまとめる仕組みが必要か。
7. **ハブからサブセッションへの指示**: 実装しないことに決めました。hookを使えば作業中のサブセッションへ指示を届けられますが、止まっているサブセッションを起こす手段はありません。止まっているサブセッションを起こすには、親か人間の`send_message`が必要です。そこで現行の方式を続けます。親が`session-hub answer` / `command`で指示を記録し、出力された行を`send_message`で送ります。
8. **規模**: ハブは受信のたびに、すべてのイベントから状態を作り直します。この方式は数千イベント程度までは問題ありません。それを超える場合は、差分更新に切り替えます。

| ストア | イベントを保存するディレクトリ（`HUB_STORE`、既定は`.hub`）。`events/*.jsonl`のファイル群が中核です |
| ダッシュボード | ハブが配信するWebページ。セッション一覧とタイムラインからなります |
| `session-hub` | 本ツールのコマンド。子の報告、親の確認と回答、ハブサーバーの起動、hookの処理を担います |
| プラグイン | 本リポジトリをClaude Codeのプラグインとして読み込んだもの。スキル、hook、コマンドをまとめて子セッションに配ります |

### データとプロトコル

| 用語 | 意味 |
|---|---|
| メッセージ | サブセッションからハブへ届く更新1件。保存されると、メッセージは1件のイベントになります。受信すると、ダッシュボードは関係する要素をしばらくグローで光らせます。親への`send_message`（`[HUB/1]`行）は、メッセージと区別するため「エスカレーション通知」と呼びます |
| グロー | メッセージが届いたときの強調表示。送り主のセッションカード、タイムラインの該当行、スイムレーンの帯、メッセージが入ったコレクションの項目が、遷移後の状態の色で約6秒間光ります（ハートビートは対象外） |
| イベント | 子または親からの報告1件（JSON 1行）。種類はstart / report / ask / answer / command / ready / pr / heartbeat / done / fail / finding |
| ステータス（ステータスレコード） | あるセッションの現在の状態。ハブはイベントを古い順に適用して（畳み込んで）ステータスを求め、保存はしません |
| 畳み込み（fold） | イベントを1件ずつ順に適用し、最新の状態を計算すること |
| イベントソーシング | 状態を保存する代わりに起きた出来事を追記し、状態は出来事から計算する設計。タイムラインをたどれるのはこの設計のためです |
| 追記のみ（append-only） | 一度書いたイベントを書き換えも削除もしない保存の規律 |
| 書き手（writer） | イベントファイルの持ち主。子は`<id>.jsonl`に書き、親の回答と指示は`<id>@parent.jsonl`に入ります |
| seq | 書き手のファイルごとの連番。イベントIDは`<file name>#<seq>`です（例: `session_01ABC#3`） |
| state | セッションの状態。§1.2の12種類の値のいずれかです。例: working、needs_human、review_ready |
| phase | 作業の段階。plan / implement / test / fix / docs / self_reviewなど |
| attention | 人間または親への質問。種類、質問文、選択肢、既定値、子が止まっているかどうか（blocking）を持ちます |
| qid | 質問の番号。回答は、どの質問に答えるかをqidで示します |
| blocking / non-blocking | 回答が来るまで子が止まっている質問 / 子が既定値で先へ進めている質問 |
| tasks / 進捗 / 残作業 | タスクの一覧と、完了数および総数。残作業は未完了タスクの規模（S=1、M=3、L=8）の合計です |
| heartbeat（ハートビート） | セッションがまだ生きていることを示す自動イベント。トークン使用量も運びます |
| usage | トークン使用量（input / output / cache_read / cache_write）。任意で費用とコンテキストの使用率も含みます |
| `HUB/1` | 親子間のメッセージの書式とその版。`[HUB/1] <id> <state> <short text>`（子→親）と`[HUB/1] cmd=<command> ...`（親→子） |
| エスカレーション（通知） | 親を起こすべき遷移（人間待ち、レビュー可、失敗、完了）のときだけ、子が親へ送る1行のメッセージ |
| コマンド（cmd） | 親から子への指示。answer / report / pause / resume / rebase / abort |

### 判定と表示

| 用語 | 意味 |
|---|---|
| 要対応 | 人間か親が何かをすべきセッション。人間待ち、失敗、レビュー可、停滞の疑いのいずれか |
| レビューゲート | PRをレビューに出してよいかの機械的な判定。PRがある、CIが通る、コンフリクトがない、未解決のコメントがない、未回答の質問がない、自己チェックが済んでいる、残りのタスクがない、のすべてを確かめます（§4.1） |
| レビュー条件未達 | 子は「レビュー可」と申告したが、ゲートを通っていない状態。ダッシュボードは満たしていない理由を表示します |
| 自己申告 / 自己チェック | 子が`session-hub ready`で申告する内容。自己レビュー、テストの追加、PRの説明が済んだことを示します |
| 停滞（stale） | 作業中のはずなのに、一定時間（既定30分）報告がないセッション。クラッシュしている可能性があります |
| 優先順位 | ダッシュボードの並び順（§4.3）。子を止めている人間待ちが最上位です |
| スピナー | 子が手を動かしている（計画中、作業中、修正対応中）ことを示す回転アイコン |
| フィード | タイムラインの形式の1つ。イベントを時系列に並べます |
| スイムレーン | タイムラインの形式の1つ。セッションごとに1本の横帯を描き、状態の変化を色で示します |

### 通信と仕組み

| 用語 | 意味 |
|---|---|
| push | 子が変化のたびにハブへ送り、ハブがただちに画面へ転送する方式。受け手が定期的に確認しに行くポーリングの反対です |
| ポーリング | 一定の間隔で変化を確認する方式。本ツールでは補助機能だけに使います。`--watch-files`、`--pull-every`、ブラウザーがSSEを使えないときの代替です |
| SSE（Server-Sent Events） | サーバーが接続を開いたままにし、データができるたびにブラウザーへ送る仕組み。ダッシュボードはSSEで即時に更新します |
| snapshot / update | SSEで送るデータ。接続直後に全体の状態（snapshot）を送り、以後は変化分（update）を送ります |
| outbox | ハブに届かなかったイベントを保持する、子の側のファイル。子は次の送信時に、まずoutboxのイベントを再送します |
| `HUB_URL` / `HUB_TOKEN` | 子と親が使う、ハブのUniform Resource Locator（URL）と認証トークン |
| `HUB_STORE` | ストアのディレクトリ。`HUB_URL`がないときは、子もここへ直接書きます |
| `HUB_SESSION_ID` | 現在のセッションのID。未設定なら、Claude Codeの環境変数から求めます |
| hook | Claude Codeが特定のタイミングで自動実行するコマンド。本ツールはSessionStart、PostToolUse、Stopを使います |
| SessionStart hook | セッションの開始時に動きます。コマンドを使えるようにし、セッションが未登録なら登録を促す短い文をコンテキストに加えます |
| PostToolUse hook | ツールの呼び出し後に動きます。TodoWriteのようなタスク操作を、進捗としてハブへ送ります |
| Stop hook | ターンの終了時に動きます。ハートビートを送り、子が作業中のまま止まろうとしていたら、1回だけ報告を求めます |
| スキル | 必要なときに読み込まれる指示のまとまり。子用の`session-hub-report`と、親用の`session-hub-orchestrate`があります |
| `append_system_prompt` | `create_session`が子に対して常に効かせる追加の指示。本ツールは5行の報告ルールを渡します |
| `send_message` | セッション間でメッセージを送る機能。届くと受け手のターンが動くので、トークンを使います。エスカレーションと指示だけに使います |
| `get_session` / `status_bucket` | セッションの状態を取得する呼び出しと、その大まかな状態（working / blocked / failedなど）。停滞の確認に使います |
| `list_events` | 子のトランスクリプトを読む呼び出し。重いので、原則として使いません |

### ナレッジとコレクション

| 用語 | 意味 |
|---|---|
| コレクション | 受け取った更新のうち、どれを集め（match）、どうまとめ（reduce）、どう見せ（view）、ほかにどこへ書き出すか（sinks）の定義と、その結果。イベントストアの投影です |
| 投影（projection） | 保存したイベント列から、目的に合った形で計算したデータ。元のイベントは変わりません |
| match | イベントがコレクションに入る条件 |
| reduce | まとめ方。log（時系列のまま残す）/ latest（キーごとに最新の1件）/ aggregate（キーごとに1件へ統合） |
| key | reduceが「同じ項目」とみなす単位。ナレッジでは明示的なキー、なければタイトル（空白と大文字小文字を無視） |
| view | 表示形式。cards（グループ分けしたカード）/ table（表） |
| sink | コレクションの追加の書き出し先（MarkdownまたはJSONLのファイル） |
| `collections.json` | ストア直下に置くコレクションの定義。組み込みのコレクションの追加、上書き、無効化に使います |
| ナレッジ | 組み込みのコレクション。サブセッションが作業中に見つけた知見や注意点を、1か所に集めます |
| finding | ナレッジに入るイベントの種類。`session-hub learn`で送ります |
| kind（findingの） | 知見の種類。caveat（注意点）/ issue（未解決の問題）/ decision（決定事項）/ howto（手順・ノウハウ）/ insight（知見） |
| scope | 知見が当てはまる場所（パス、モジュール、サービス名）。`knowledge --scope`はscopeを使い、関係する知見だけを読みます |
| obsolete（廃止） | もう当てはまらなくなった知見。表示と`knowledge`の出力から外れますが、履歴は残ります |
| 報告元（reporters） | その項目を報告したセッション。報告元が多いほど、多くの作業者が同じことに遭遇したことを示します |
